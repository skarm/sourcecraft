# Запускаемые примеры

[English](README.md) · [Русский](README.ru.md)

Команды запускаются из корня репозитория с Go 1.26 или новее. Для запросов нужен
PAT с правами на выбранный репозиторий; в CI/CD SourceCraft можно использовать
предоставленный `SOURCECRAFT_TOKEN`. Токен читается только из окружения:

```sh
export SOURCECRAFT_TOKEN='your_access_token_here'
```

`-org` и `-repo` — slug организации и репозитория. `-pr`, `-issue` и `-run` —
номера ресурсов в выбранном репозитории, передаваемые строкой. Примеры `pullrequests`, `attachments` и `cicd` поддерживают `-h`, общий
тайм-аут `-timeout` и отмену через Ctrl+C.

## Создание и слияние PR

[pullrequests/main.go](pullrequests/main.go) содержит отдельные команды создания
и слияния существующего PR. Ветки должны существовать и быть отправлены в
SourceCraft через Git.

```sh
go run ./examples/pullrequests create \
  -org my-org -repo my-repo \
  -source feature -target main \
  -title 'Add feature' -description 'Description of the change'
```

Команда выводит номер PR, ID и статус. По умолчанию PR публикуется; для черновика
передайте `-draft`. Создание PR не запускает команду слияния.

Используйте выведенный номер PR для слияния:

```sh
go run ./examples/pullrequests merge \
  -org my-org -repo my-repo -pr 42 \
  -squash=true -timeout 5m
```

Пример вызывает `MergePullRequest`, выводит ID операции и ожидает её завершения
через `WaitPullRequestMerge`. При успехе выводятся hash merge-коммита и hash
целевой ветки, использованный как merge base. Ошибки проверок и асинхронной
операции возвращаются вызывающему процессу; принудительное слияние не задаётся.

Непереданные `-squash` и `-delete-source` сохраняют настройки репозитория:
соответствующие поля остаются `nil`. Явные `-squash=false` и
`-delete-source=false` отправляют `false`. Для удаления исходной ветки после
слияния передайте `-delete-source=true`.

```sh
go run ./examples/pullrequests create -h
go run ./examples/pullrequests merge -h
```

## Загрузка вложения задачи

[attachments/main.go](attachments/main.go) открывает локальный файл, передаёт его
потоком через `UploadIssueAttachment` и закрывает reader при выходе. После загрузки
выводятся ID, имя и размер вложения, затем `GetIssueAttachment` получает временный
URL скачивания.

```sh
go run ./examples/attachments \
  -org my-org -repo my-repo -issue 7 \
  -file ./report.txt -timeout 2m
```

Задача должна существовать. Получение URL — отдельный запрос: если он завершится
ошибкой, файл уже может быть загружен. В сообщении сохраняется ID вложения;
автоматического повтора загрузки нет. Пример выводит ссылку, скачивание файла
остаётся отдельным действием.

## Запуск CI/CD и получение результатов

[cicd/main.go](cicd/main.go) запускает один workflow по имени из
`.sourcecraft/ci.yaml`, ожидает завершения run, затем читает workflows, задачи,
кубы, страницы логов и свежие ссылки на артефакты.

```sh
go run ./examples/cicd \
  -org my-org -repo my-repo -workflow checks \
  -branch feature -config-branch main \
  -input environment=staging -input publish=false \
  -timeout 15m -interval 2s
```

Workflow должен существовать в выбранной конфигурации и допускать такой запуск
согласно настройкам SourceCraft. `-branch` выбирает ветку кода,
`-config-branch` — ветку конфигурации CI. Если флаг не передан, для соответствующей
ревизии используется default branch репозитория. `-input` можно повторять;
пустые значения (`-input name=`) и `=` внутри значения сохраняются.

Номер run выводится сразу после запроса. Чтобы прочитать существующий run,
включая повторное получение результатов после тайм-аута, используйте:

```sh
go run ./examples/cicd \
  -org my-org -repo my-repo -run 123 -timeout 15m
```

Режим `-run` выполняет запросы чтения и не запускает новый CI. Для него не
принимаются `-workflow`, `-branch`, `-config-branch` и `-input`.

Пример ожидает состояния `created`, `prepared`, `processing` и
`awaiting_approval` в пределах общего тайм-аута. После конечного состояния
результаты читаются также для неуспешного CI. Код 0 возвращается при статусе
`success` и отсутствии ошибок получения данных; другие конечные статусы или
ошибки запросов результатов дают ненулевой код.

Логи читаются последовательно по страницам. `done` относится ко всему кубу,
поэтому чтение не заканчивается после первой страницы с `done=true`.
`page_complete` определяет переход к следующей странице. Если логи ещё пишутся,
программа сообщает об этом и предлагает повторное чтение через `-run`.
Отсутствие следующей страницы после полной конечной страницы считается концом
логов; ошибка первой страницы не скрывается. Основание —
[контракт GetCubeLogs](https://sourcecraft.dev/portal/docs/en/api-ref/CICD/GetCubeLogs).

Ошибка логов одного куба сохраняется, но программа продолжает получение
артефактов и результатов остальных кубов. Кубы, не выполнявшиеся из-за пропуска,
отклонения или ожидания запуска/одобрения, выводятся без запросов их вывода.
Ссылки на артефакты временные; файлы автоматически не скачиваются.

Тайм-аут и Ctrl+C прекращают локальное ожидание. Уже принятая сервером операция
слияния или CI может продолжать выполняться.

## Остальные примеры

Эти примеры обходят списки с пагинацией:

- [repositories](repositories/main.go) — пагинация списка доступных репозиториев.
- [appsec](appsec/main.go) — пагинация групп уязвимостей по UUID или ID репозитория.

Примеры компилируются при `go test ./...`. Тесты CI/CD используют тестовый HTTP-
транспорт и виртуальное время: проверяются ожидание одобрения и тайм-аут,
пагинация завершённых логов, ошибки вывода и продолжение сбора результатов.
